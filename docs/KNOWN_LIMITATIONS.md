# FieldOps AI — Known Limitations & Operational Constraints

**Document Version:** 1.0.0  
**Scope:** Architecture, Integrations, Machine Learning, and Infrastructure  
**Date:** October 2026  

This document provides transparent technical disclosure of known constraints, unverified external systems, synthetic data boundaries, and operational prerequisites for FieldOps AI.

---

## 1. Machine Learning & Synthetic Data Limitations

### 1.1 Synthetic Dataset Origin
Both the Job Duration Prediction Model and the Missed-Appointment Risk Model were trained, validated, and evaluated on a **synthetic dataset of 3,000 samples** generated by `app/ml/data_generator.py`.
- While features incorporate realistic Metro Atlanta geography, equipment aging curves, technician skill matrices, and seasonal weather multipliers, **these numbers do not reflect empirical field operating data**.
- Claimed metrics (e.g. 6.90 min MAE, 0.255 PR-AUC) must strictly be reported as benchmark results on synthetic data.

### 1.2 Risk Classifier Imbalance & False Positive Rate
- In the synthetic test distribution, missed appointments represent only ~13.3% of total bookings.
- Although `HistGradientBoostingClassifier` achieved a **PR-AUC of 0.255** (substantially outperforming the marginal prior baseline of 0.133), its precision at a standard 0.5 decision threshold is **14.9%** with a recall of **53.3%**.
- **Operational Risk:** Relying autonomously on the risk classifier in production would generate substantial false alarms, causing dispatchers to unnecessarily double-book or pre-emptively contact customers who intended to show up.
- **Remediation Needed:** In production, probability threshold tuning, cost-sensitive threshold selection, Platt scaling calibration, and human-in-the-loop review are mandatory before automated dispatch decisions.

## 2. External Third-Party Integrations Status

All external SaaS providers are currently decoupled behind Python `Protocol` interfaces and tested using **deterministic in-memory mock adapters**.

| Provider Domain | Current Implementation | Production Requirement for Live Operation |
| :--- | :--- | :--- |
| **SMS & Messaging** | `MockNotificationAdapter` (in-memory ring buffer) | Active Twilio account with provisioned SID, Auth Token, and 10DLC registration. |
| **Email Delivery** | `MockNotificationAdapter` (in-memory buffer) | SendGrid or AWS SES API key with verified domain DKIM/SPF records. |
| **Mapping & Routing** | `MockMapsAdapter` (Haversine spherical distance) | Google Maps Distance Matrix API key or self-hosted OSRM routing server. |
| **Calendar Sync** | `MockCalendarAdapter` (simulated event IDs) | Google Workspace Service Account / Microsoft Entra App Registration with OAuth2. |
| **CRM Sync** | `MockCRMAdapter` (simulated CRM IDs) | Salesforce Connected App or HubSpot Private App token with bi-directional webhooks. |
| **Speech-to-Text** | `MockSTTAdapter` (ASCII voice parsing) | OpenAI Whisper API key or self-hosted Faster-Whisper GPU container. |
| **Text-to-Speech** | `MockTTSAdapter` (synthesized 44-byte WAV headers) | ElevenLabs API key or OpenAI TTS endpoint. |
| **Conversational LLM** | `MockLLMAdapter` (rule-based slot-filling agent) | OpenAI API key (`gpt-4o`) or Anthropic Claude API key with adequate rate limits. |

> [!IMPORTANT]
> No external provider can be considered live-verified in the current repository environment because live credentials are intentionally omitted from development configurations.

## 3. Database & Storage Architecture

### 3.1 Single-Node MongoDB vs. Replica Set Transactions
- The development setup runs a standalone MongoDB instance (`mongo:7.0`).
- MongoDB multi-document ACID transactions across distinct collections require a **Replica Set** deployment.
- **Compensating Design:** The current codebase utilizes single-document atomic updates (`find_one_and_update`), optimistic concurrency versioning (`lock_version`), lease-based reservation hold states, and transactional outbox staging.
- **Production Requirement:** For enterprise high-availability, MongoDB must be deployed as a 3-node replica set with automated failover and secondary reads.

## 4. Performance & Scalability Boundaries

### 4.1 In-Process CPU Contention Under ML Inference
- Load testing verified sub-100ms P50 latency (64.44 ms) for standard database and CRUD operations.
- However, when 10 concurrent requests invoked scikit-learn Gradient Boosting inference simultaneously on a single CPU core, P95 latency increased to ~15.2 seconds due to Python GIL and CPU saturation.
- **Remediation Needed:** In high-volume production, ML inference must be decoupled from the primary web event loop, either via dedicated Triton/TorchServe model servers, Celery asynchronous workers, or ONNX Runtime with multi-threaded C++ execution.

### 4.2 In-Memory Rate Limiting
- The default `RateLimiterMiddleware` maintains client IP counters in a local Python dictionary.
- In a horizontally autoscaled deployment across multiple container instances, local in-memory rate limiting does not share state between nodes.
- **Production Requirement:** Rate limiting must be transitioned to a Redis-backed sliding window or token-bucket algorithm using Redis EVAL scripts.

## 5. Security & Session Handling

### 5.1 Static JWT Secret in Development
- `docker-compose.yml` and `.env.example` specify default placeholder secret strings (`dev-secret-key-change-in-production...`).
- **Production Requirement:** Production deployments must inject secrets via a secure secrets manager (AWS Secrets Manager, HashiCorp Vault, or Kubernetes Secrets) with mandatory rotation policies.

### 5.2 Ephemeral Chat Sessions
- AI intake sessions are stored with in-memory fallbacks or TTL documents in MongoDB.
- Voice session audio payloads currently store base64 strings in memory during the conversation turn. Extended multi-minute voice recordings should be streamed directly to S3 or object storage to prevent memory spikes.
